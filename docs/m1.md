# M1 - protocol core

Status: **every leg works, the maker daemon runs itself, and a taker with no
node can now claim.** What is left is the coordinator (see
[Not yet](#not-yet)).

The split is on purpose. `swapsite-core` has no sockets, no filesystem and no
subprocesses, so it compiles to WASM unchanged for the browser-side taker
signer. Everything impure lives in `swapsite-adapters` behind the `Chain` and
`LightningNode` traits.
## The browser-side taker

A taker has no node, no docker and no wallet software. Everything cryptographic
runs in `swapsite-wasm`, and a relay supplies the two things a page cannot do
for itself: reading the chain and broadcasting.

```text
GET  /height        -> {"height": N}
GET  /tx/<txid>     -> {"txid", "confirmations", "hex"}
POST /tx            -> {"txid"}      body is raw transaction hex
```

A relay can lie about what it sees and can refuse to broadcast, but it cannot
take funds: the taker rebuilds the HTLC address from public values, checks the
deposit transaction really pays it, and signs its own claim with a key the relay
never sees.

### No wasm-bindgen, on purpose

The module exposes four symbols and is loaded with plain
`WebAssembly.instantiate`:

```text
alloc(len) -> ptr             write a request here
dispatch(ptr, len) -> ptr     returns [u32 little-endian length][json]
dealloc(ptr, len)             free either buffer
```

Requests and responses are JSON, so the whole API is the dispatcher, which is
ordinary Rust and unit tested natively. The browser and the tests run the same
code.

The module has **zero imports**. That is not a coincidence: `rand-std` is a
feature of `swapsite-core` (`rand`, on by default) and the wasm build turns it
off, because on `wasm32-unknown-unknown` it drags in `getrandom`, which drags in
`wasm-bindgen`, which needs its JS shim and a CLI to generate it. Instead the
page supplies 32 bytes from `crypto.getRandomValues` and the module derives the
key, which is the part a page cannot do for itself.

## The leg

```text
OP_IF
    OP_SHA256 <payment_hash> OP_EQUALVERIFY <claimant> OP_CHECKSIG
OP_ELSE
    <refund_locktime> OP_CLTV OP_DROP <refunder> OP_CHECKSIG
OP_ENDIF
```

P2WSH, so the funder pays to a 32-byte script hash and either side spends with a
witness. The preimage path belongs to whoever is owed value on the leg; the
timelocked path belongs to whoever funded it. Either party can always exit, but
the non-funder only via the preimage and the funder only via the timeout.

`swapx` prints exactly that:

```text
OP_IF OP_SHA256 OP_PUSHBYTES_32 <hash> OP_EQUALVERIFY OP_PUSHBYTES_33 <claimant> OP_CHECKSIG
OP_ELSE OP_PUSHBYTES_2 f401 OP_CLTV OP_DROP OP_PUSHBYTES_33 <refunder> OP_CHECKSIG OP_ENDIF
```

## The Lightning leg

A Lightning leg is a BOLT11 invoice locked to the same payment hash as the
HTLC. The maker issues it as a **hold invoice**:

| Command | State | Meaning |
| ------- | ----- | ------- |
| `addholdinvoice` | `OPEN` | invoice exists, nothing committed |
| payer pays | `ACCEPTED` | the payer's funds are held, preimage still hidden |
| `settleinvoice` | `SETTLED` | the preimage is revealed to the payer |
| `cancelinvoice` | `CANCELED` | the payer's funds are released, no preimage revealed |

Holding is what makes this work. The payer commits funds but cannot take them
back at will, and the maker cannot take them without revealing the preimage that
spends the on-chain leg. The taker only ever *pays* an invoice, so it needs no
HODL-invoice support at all; that burden sits entirely on the maker.

### The join

Nothing is negotiated and nothing is trusted. The preimage Lightning reveals has
to be the one that unlocks the HTLC:

```rust
pub fn check_joined(htlc: &Htlc, revealed: &Preimage) -> Result<(), JointError>
```

That single equality is the whole atomic link. `swapx claim` refuses to build a
claim transaction whose preimage does not unlock the HTLC, so a mistake here is a
hard error rather than a lost deposit.

## The maker daemon

The daemon is the maker's side with a human removed. Its whole job is a loop:

1. **observe** - chain height, confirmations of the deposit and refund, and the
   invoice state, all read fresh from the two nodes;
2. **reconcile** - move the stored state to match what was observed;
3. **plan** - decide the single next action;
4. **act** - broadcast, settle or refund, then save the record.

`plan` is a pure function of the record and a small `Observed` struct, so the
ladder of decisions is unit tested rather than hoped about:

| Situation | Action |
| --------- | ------ |
| invoice settled | done, whatever the record said |
| deposit broadcast but not mined | rebroadcast the deposit |
| taker paid, deposit confirmed | settle |
| nothing settled, past the timeout | refund |
| otherwise | wait |

Two rules make it safe to kill and restart:

- **Persist before broadcasting.** Every signed transaction is written into the
  swap record *before* it goes to the network, so a crash always leaves enough
  to rebroadcast. A refund is built once and reused on every later tick.
- **Observed reality wins.** `reconcile` adopts a terminal state it sees
  on-chain or on Lightning, so a swap settled just before a crash is not lost.
  It cannot adopt a non-terminal state, so a stale file cannot walk a swap
  backwards.

Settling beats refunding whenever both are possible. A held payment is a promise
the taker already made, and taking the deposit back instead would leave that
payment with nothing to unlock.

## Timeout invariant

`LegTimelocks::new` refuses to construct a swap unless the initiator's refund
timeout exceeds the counterparty's by at least `MIN_MARGIN_BLOCKS` (12). Time
based locktimes are rejected outright: mixes of heights and times on two chains
are a footgun with no upside here.

## State machine

`Created -> InitiatorFunded -> CounterpartyLocked -> Settled`, with `Refunded`
reachable from either funded state. Enforced properties:

- the counterparty leg cannot lock before the initiator funds;
- settlement is impossible until both legs are locked;
- terminal states absorb nothing;
- every funded state can refund.

## Verification

```bash
cargo test                          # 31 tests
./scripts/regtest-onchain.sh        # needs the docker stack up
```

`cargo test` runs the **real Bitcoin script interpreter** (`libbitcoinconsensus`)
over the spends we build, so the scripts are not just structurally asserted:

- a claim with the right key and preimage verifies;
- a refund with the right key verifies;
- a claim with the wrong preimage is rejected by consensus;
- a claim with the wrong key is rejected by consensus.

`regtest-onchain.sh` then does it on a chain, in this order: fund an HTLC at a
`bcrt1q...` address, claim it with the preimage and confirm it; fund a second
HTLC, show that the refund is **rejected before the timeout**, mine to the
timeout, then refund and confirm.

`regtest-swap.sh` then runs one complete swap, Lightning -> on-chain:

1. the maker picks a preimage and issues a hold invoice for 30,000 sat;
2. the maker funds an HTLC for the same amount plus the claim fee, claimable by
   the taker with that preimage and refundable by the maker from a timeout;
3. the taker rebuilds the HTLC address from public values alone and checks the
   funding output before committing anything;
4. the taker pays the hold invoice and the maker sees `ACCEPTED`;
5. the maker settles, and the taker learns the preimage;
6. the taker claims the HTLC with that preimage and nets exactly 30,000 sat.

Then it runs the failure path: a second invoice is paid and **canceled** by the
maker. The taker's payment fails with no preimage revealed, and the maker's
deposit stays unspendable until the timeout, when the refund confirms.

`regtest-maker.sh` runs the daemon itself, with no human in the loop:

1. a swap is created while the daemon is **not running**;
2. the taker rebuilds the HTLC address from public values, checks the deposit
   pays it, and pays the hold invoice;
3. the daemon is started cold, finds a swap it never saw created, and settles it;
4. the taker claims with the revealed preimage and nets exactly what it paid;
5. a second swap is created whose taker never pays. The daemon holds off until
   the timeout, then builds, broadcasts and confirms the refund.

`regtest-wasm.sh` runs the whole taker side from the browser's position:

1. the taker generates its claim key **in wasm**;
2. the maker creates the swap;
3. the taker rebuilds the HTLC address itself, fetches the deposit through the
   relay, and checks the deposit really pays that address;
4. it refuses a deposit that pays a different HTLC;
5. the maker settles, the taker learns the preimage, checks the join and signs
   the claim in wasm, then broadcasts it through the relay.

## Decisions

- **Rust for the core.** One implementation serves the maker daemon and, via
  WASM, the taker signer. The `swapx` CLI depends on `clap`, which will move to
  its own crate before this library targets WASM.
- **`swapx` is stateless.** Every command takes the keys and parameters it needs,
  so each party only ever handles its own secret. An earlier state-file design
  forced both keys into one file, which misrepresented the trust model.
- **Hold invoices are the maker's problem, not the taker's.** The taker needs no
  special wallet behaviour beyond paying a BOLT11 invoice.
- **`lncli` behind the `LightningNode` trait.** A development transport so the
  protocol can be tested against real LND nodes without a TLS and macaroon client
  in the loop. A REST or gRPC client implements the same trait.
- **Heights only, never times.** Rejected at construction.
- **`Preimage` is not `Copy` and its `Debug` is redacted** so a secret cannot
  leak into a log line by accident.
- **Refund sequence `0xFFFFFFFE`, claim sequence `MAX`.** The refund has to leave
  the locktime field enabled; the claim has nothing to wait for.

## rust-bitcoin 0.32 notes

Learned the hard way while building this:

- `OP_CHECKLOCKTIMEVERIFY` is `opcodes::all::OP_CLTV`. The ASM renders as
  `OP_CLTV` too.
- `SighashType` is `sighash::EcdsaSighashType`.
- `LockTime::from_height` returns `Result<LockTime, ConversionError>`.
- `Builder::push_slice` wants `&[u8; N]`, not `&[u8]`.
- `Witness::from_slice` needs a homogeneous slice, so the witness builders use
  `Vec<u8>` elements.
- The `bitcoinconsensus` crate is versioned by libbitcoinconsensus (`0.106` ==
  Core 26.0), not by rust-bitcoin. Its `verify` takes
  `(&[u8], u64, &[u8], Option<&[Utxo]>, usize)` and its error enum is `Error`.

## Not yet

- **Coordinator.** Quotes, order book, swap records for takers, recovery pages.
- **A real Lightning client.** `lncli` is a dev transport; the maker daemon wants
  REST or gRPC, and the taker wants to pay from its own wallet (WebLN).
- **Only one direction in the daemon.** It implements Lightning -> on-chain. The
  other direction needs a third-party invoice to pay, which the swap scripts do
  but the daemon does not.
- **Fee management.** Fees are fixed flags. Nothing here adapts to a mempool.
- **A real page.** `web/` is a module and a CLI, not a UI. Nothing serves it yet,
  and there is no recovery flow for a taker who closes the tab mid-swap.
