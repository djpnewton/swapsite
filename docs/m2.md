# M2 - coordinator and web UI

Status: **a swap can be quoted, brokered, verified, paid, claimed and recovered
entirely from a browser page.** Verified by hand in the integrated browser
against regtest, and by
[regtest-coordinator.sh](../scripts/regtest-coordinator.sh) and
[regtest-recovery.sh](../scripts/regtest-recovery.sh) from a shell.

## What exists

```
core/src/recovery.rs         the taker's verdict: what is left, and how long
adapters/src/http.rs         one HTTP server and client shared by every service
adapters/src/bitcoind.rs     + outspent: what an output is worth while it lasts
cli/src/bin/relay.rs         + `GET /utxo/<txid>:<vout>`
cli/src/bin/coordinator.rs   the website's service: quotes, brokering, static files
cli/src/bin/maker.rs         + `maker serve`: a JSON control plane over the daemon
web/index.html               the page
web/app.css                  the page's styles
web/app.js                   the page's plumbing: quote, verify, pay, claim, recover
web/wasm.mjs                 the wasm module, minus how its bytes are obtained
web/relay.mjs               the relay client
web/taker.mjs                the page's loader: bytes over HTTP
web/taker-node.mjs           the Node loader: bytes from disk
web/taker-cli.mjs            the same operations, for a shell to drive
scripts/regtest-coordinator.sh  the whole flow, over HTTP, end to end
scripts/regtest-recovery.sh     a lost page, a deadline, and a maker that reneges
```

## The coordinator

It is the only component a browser talks to. It quotes, it asks the maker for a
swap, it remembers what a taker needs to find its swap again, and it serves the
page. It holds no keys, no funds and no swap secrets: the only secret it ever
sees is a preimage the maker has already published by settling, and by then it is
public. It is not on the critical path either - a taker that already has a
deposit and a preimage can claim through any relay without it.

```text
GET  /config                 fee schedule, relay URL, network
GET  /quote?amount=N         what N costs, before committing (includes the bond)
GET  /swaps?claim_pubkey=K   what this taker has started (recovery)
POST /swaps                  ask the maker for a swap
GET  /swaps/<id>             one swap
POST /dev/pay/<id>           dev only: pay what the taker's wallet pays next
GET  /                       the page, plus every static file in `web/`
GET  /swapsite_wasm.wasm     the compiled taker module
```

`POST /dev/pay/<id>` pays the **bond** when the swap has no deposit yet, and
answers `{"paid": "bond"}` with no preimage - a bond payment reveals nothing
worth having. Once the deposit exists it pays the swap's invoice and answers
with the preimage, as before.

The fee is charged on top of the amount the taker receives, and the coordinator
passes the quoted fee straight through to the maker rather than keeping a margin
of its own: what the page was told is what the maker was asked for.

**The dev-pay endpoint is off unless `--dev-pay` is passed.** With it on, the
coordinator learns a preimage it would never see in production, because a real
page pays through WebLN. It exists so the whole flow can be exercised without a
second Lightning wallet.

`--dir` takes the swap records. They are written *before* the response is sent,
so a taker that never receives the reply can still find its swap afterwards.

### Static files

`web/` is served with three refusals: no `..`, no absolute paths, no hidden
files. `swapsite_wasm.wasm` goes out as `application/wasm` because one content
type is what `WebAssembly.compile` needs to stream the bytes without a fetch
round-trip.

## The page

Every piece of cryptography runs in the wasm module. `app.js` is the plumbing
around it, and it holds the only two things that matter:

- the **claim key**, generated in the page and never sent anywhere;
- the **preimage**, from the payment that reveals it or from the maker that has
  settled and published it.

Both live in `localStorage` under one key. Losing the preimage after the maker
settles means losing the swap to the maker's timeout, so it is worth persisting.
A real product would protect these with a passphrase or a hardware signer.

The flow, as run in the browser against regtest:

```text
1. quote            30,000 sat on chain for 30,030 sat over Lightning (fee 30)
2. create           the maker offers terms and a 4,000 sat bond - nothing funded
3. pay the bond     the maker funds a 32,000 sat HTLC, refundable at height 506
4. mine a block     the deposit reaches 1 confirmation
5. check deposit    the page rebuilds the script, sees 32,000 sat, 1 conf
6. pay              the preimage appears in the page
7. claim            signed in wasm, broadcast through the relay
8. mine a block     the destination address shows exactly 30,000 sat
```

32,000 rather than 30,000 because the deposit also carries the claim fee the
taker will spend. Step 5 is the whole trust model: the page does not believe the
coordinator about the deposit, it rebuilds the address from public values and
checks the transaction pays it. It is also what gates step 6: the page refuses
to pay for a swap whose deposit it has not checked.

### The bond, and why funding waits for it

Nothing is funded until the bond is in. That inverts the obvious order, so it is
worth saying what it buys: funding first makes abandoning a swap free, because
the taker risks nothing while parking the maker's capital for the whole
locktime. With the bond, walking away costs 4,000 sat instead of nothing.

The bond is a **plain** invoice rather than a hold one, so paying it is final and
locks none of the taker's liquidity - it is a fee, not a deposit. Its hash is
derived from the swap's own secret (`sha256(sha256(preimage))`) for two reasons:
the maker never has to read the node's bookkeeping to answer "has it been paid",
and settling the bond cannot reveal the secret that unlocks the on-chain leg.
Both are pinned by tests, the second one explicitly.

The window is bounded too: `bond_by` is the last height the maker will fund at,
and the on-chain locktime is measured from there. Without it a slow bond would
quietly eat the margin between the deposit and the refund. Measuring from
`bond_by` is also what makes the taker's window predictable: the maker's default
margin is the invoice's CLTV delta plus `MIN_MARGIN_BLOCKS` plus a payment
window, so a taker that pays at the last moment the maker may fund still has the
whole window to pay in.

## The JS split, and why

The page and the shell must drive *exactly* the same code, but they get the
module's bytes in completely different ways. One file holding both meant the
page imported `node:fs/promises`, and the browser rejected the module with a
CORS error before anything ran:

```text
Access to script at 'node:fs/promises' from origin 'http://127.0.0.1:8090'
has been blocked by CORS policy
```

So the split is by *dependency*, not by audience:

| File              | Imports          | Used by        |
| ----------------- | ---------------- | -------------- |
| `wasm.mjs`        | nothing          | both           |
| `relay.mjs`       | nothing          | both           |
| `taker.mjs`       | `wasm.mjs`       | the page       |
| `taker-node.mjs`  | `node:fs`        | `taker-cli.mjs` |

`wasm.mjs` imports nothing, which is the property that lets it run in both. Both
loaders compile the module before instantiating it, so the "this module imports
nothing" check runs first and reports itself, rather than the failure surfacing
as an opaque instantiation error.

## Recovery

A taker that pays and then closes the tab has the preimage and nothing else. The
deposit is still theirs, but only a claim converts it into coins, and nothing
else can do that for them: the coordinator holds no key and never sees the
preimage.

So recovery is a **verdict**, not a service. `core/src/recovery.rs` answers "is
there still a move, and how long is it good for" from four things: the swap's
state, whether the preimage has reached this page, whether the deposit output is
still unspent, and the current height against the HTLC's own locktime.

The verdict is computed in the wasm module, so the page and the tests run the
same code, and it is recomputed on every poll:

| Verdict | Meaning |
| --- | --- |
| `wait_for_deposit` | The maker has not funded yet. |
| `wait_for_payment` | Funded, no preimage. Still in flight or never made. |
| `too_late_to_pay { blocks_left }` | Funded and unpaid, but a payment made now would expire after the refund. Do not pay. |
| `expired` | The same window, once the refund path is open. Nothing to pay and nothing to claim. |
| `find_preimage` | Settled, so the preimage exists, but this page has not got it. |
| `claim { blocks_left }` | Claim now and it cannot lose a race. |
| `racing { blocks_since }` | The refund path is open. A claim still wins, but only if it gets there first. |
| `gone` | The deposit has been spent. There is nothing left to claim. |

The page polls every three seconds and, when the verdict says a claim is
available and it has a destination address, **claims without being asked**. That
is safe because a claim only ever moves value towards the taker.

### Why a window can be too late to pay into

`too_late_to_pay` is the mirror of `racing`, and the one verdict that tells a
taker to do nothing: the deposit is funded and the swap is unpaid, but the
invoice's final CLTV delta is part of the swap, so the taker knows exactly when
a payment made at this height would expire. If that is inside
`MIN_MARGIN_BLOCKS` of the refund, a maker could refund the deposit and still
settle the payment, taking both legs. The page says so and hides the actions,
rather than offering a button that throws when pressed. `Settled` is deliberately
not covered: the hashlock path has no CLTV, so the preimage is worth having
however late it arrives.

A window that has closed is a different thing from one that is merely short, and
it reads differently: there is nothing to count down to, and the deposit is the
maker's to take back whenever it likes. That is `expired`, which is why the card
stops saying "initiator funded" and says so instead - the maker's own record has
not changed, and will not until the refund.

### Where the preimage comes from

`find_preimage` used to be a dead end for anyone who paid from somewhere other
than the page: the maker knew the preimage but would not say it, so the taker had
to carry it across by hand. That was wrong. Settling *is* the reveal - a hold
invoice is settled by handing over the preimage, which is what tells the
Lightning network the payment is claimable - so from that moment the preimage is
public and withholding it protects nothing.

So `PublicSwap` carries it, on a **settled** swap and on nothing else:

```text
before settling   the field is absent
settled           "preimage": "<64 hex>"
```

Absent rather than null, so a swap's public view cannot be read as "the secret
is out" before it is. `Settled` is only ever reached by observing a settled
invoice, so the field cannot outrun the reveal.

The page takes it on every poll and the verdict turns into `claim` on its own,
which is what removes the copy-paste. The inline paste field stays as the
fallback for a maker that is unreachable or running an older build; a wrong
preimage is harmless, because `claim` checks it against the HTLC before signing
anything.

### What the deadline actually protects against

The hashlock path has no CLTV. A claim is valid at any height, forever, so
passing the deadline is not the same as losing - it turns a safe claim into a
race. That is why the verdict is `racing` rather than `lost` at the boundary.

It also turns out that this maker **never** refunds a swap it was paid for:
`plan` returns `Done` the moment the invoice settles. The danger is therefore
not the daemon but the script: the refund path is the maker's key behind a CLTV,
and nothing on chain consults the daemon's opinion, so a maker that reneges can
take a deposit it has already been paid for. `regtest-recovery.sh` makes it do
exactly that, because a warning about a danger nothing can demonstrate is not
worth much.

### Why the taker checks the chain itself

The maker's records only follow the refund the maker built itself, so a refund
broadcast by anyone else leaves no trace in any record: the maker's view still
says `settled`. Nothing off-chain can report the deposit as gone. So the taker
asks the chain directly, through a new relay endpoint:

```text
GET /utxo/<txid>:<vout> -> {"unspent": bool, "sats": N|null}
```

A relay that lies about this can only make a taker try a claim that fails. A
missing answer is treated as *unspent*, because being wrong that way costs a
failed transaction while being wrong the other way tells a taker to give up on a
swap that is still theirs.

### Coordinator behaviour this needed

`GET /swaps` returned the coordinator's own stored record, which was written at
creation and never updated, so a paid swap was still reported as `created`. A
verdict built on that would have said `wait_for_deposit` for a swap that had
settled. Listing now refreshes each swap from the maker first, the same way
`GET /swaps/<id>` already did.

## Lessons

- **The page is the test.** The `node:fs` bug passed `node --check`, passed the
  CLI scripts and passed every unit test. Only loading it in a browser found it.
- **A method is not a field.** `Recovery::actionable()` was a Rust method, so it
  never crossed the JSON boundary, so `recovery?.actionable` was always
  `undefined` and auto-claim silently skipped every swap. Nothing type-checks
  across JSON: the wasm tests now assert the verdict's whole key set, not just
  the behaviour behind it.
- **A poll must not repaint what nobody changed.** Replacing the swap list every
  three seconds took the cursor out of the address field mid-typing, and made
  clicks flaky. `render` now compares the markup first.
- **A test can pass for the wrong reason.** The first version of the early-refund
  check accepted any broadcast failure, so an empty transaction counted as "the
  timelock refused it". It now requires the node to say `non-final`.
- **A daemon's argv is what `pkill` sees.** The binaries run from `target/debug`,
  so a pattern of `bin/relay` matches nothing and the daemon survives to race the
  next run. Match the flags instead.
- **Verified is not the same as reported.** Claims were checked by asking
  bitcoind what the destination address received (`0.00030000`), not by reading
  the page's own message that it had claimed.

## Not yet

- A second maker, and any notion of an order book. One maker is a quote.
- Nothing tells a taker to come back: the page acts when it is opened, and an
  unopened tab is still a loseable swap. That wants a notification channel.
- The daemon infers a refund from "the deposit is gone and nothing settled".
  That is sound, and it fixes the case that mattered, but the case it still
  cannot see is a refund of a deposit the maker was *already paid for*: the
  invoice is settled, so `reconcile` stops there and the record reads `Settled`
  while the maker has taken the deposit too. Nothing breaks - settled is
  terminal, so nothing is retried - but an anomaly like that should be visible.
  Telling the two apart on chain means reading which branch of the script the
  spending witness took.
- No CSP. The client is static and has no dependencies at all - no CDN, no inline
  script - so there is nothing to pin, but a `Content-Security-Policy` header on
  the served files is still the cheap half of the XSS mitigation in
  [plan.md](plan.md) and is not there.
- The WebLN branch in `app.js` exists but has never run: no browser in the test
  setup has a WebLN wallet. The invoice is now shown on the card, so paying from
  somewhere else is a real route - `docs/regtest.md` walks it - and the
  paste-the-preimage half of it is exercised by that walk, but nothing drives the
  WebLN half.
- A maker will not hand over the preimage of a swap it has settled: fixed. It
  does now, on settled swaps only, which removes the copy-paste for a swap paid
  from another wallet. The paste field remains as the fallback for a maker that
  is unreachable.
- The page polls `GET /swaps/<id>` for every swap it remembers, including ones
  the coordinator has never heard of, which returns 404 every three seconds
  forever. Harmless, but it should stop asking.
